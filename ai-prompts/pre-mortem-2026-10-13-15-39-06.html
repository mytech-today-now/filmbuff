Failure mode
When HTTP transport is explicitly enabled without FILMBUFF_MCP_TOKEN, the production request handler skips its authorization check. The listener also uses server.listen(port) without a host restriction, so Node selects its normal all-interface binding.
Evidence or rationale
cli/src/commands/mcp-server.ts reads FILMBUFF_MCP_TOKEN and checks the Authorization header only inside if (mcpToken), then starts server.listen(port). The module registers video initialization, generation, approval, rejection, status, compile, and recovery tools for the selected project. Its comment says missing or invalid tokens receive HTTP 401, but the missing-configuration case bypasses the check. cli/src/__tests__/mcp-server.test.ts tests a test-local HTTP server with a configured token, not the production server with the variable absent. Testable assumption: a peer can reach an HTTP listener started on a network interface and submit a valid MCP request. Source anchors at the reviewed revision eb44aa9: cli/src/commands/mcp-server.ts:211-241; cli/src/__tests__/mcp-server.test.ts:221-284.
Why this matters
A reachable unauthenticated client could invoke state-changing video tools against the project passed to the server. Generation may consume provider credits, while lifecycle tools can move project media. A local stdio server does not need this HTTP exposure.
Recommended mitigation
Fail closed when HTTP is requested without a token, bind to loopback by default, and require an explicitly reviewed TLS-terminating deployment boundary before allowing remote access. Keep stdio transport behavior unchanged. Return a stable unauthorized or configuration error before handing any request to the MCP transport.
